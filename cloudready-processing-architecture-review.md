# Ревью архитектуры: CloudReady Document Processing & Printing

Ревью документа [cloudready-processing-architecture-plan.md](cloudready-processing-architecture-plan.md) (состояние на 2026-09-18). Ниже — то, что в плане не покрыто или покрыто слабо, плюс рекомендации. Сильные стороны плана (outbox pattern, идемпотентность per-handler, saga вместо блокирующего оркестратора, разделение hard/soft readiness-зависимостей, модель доверия к файлам в разделе 8.1) не повторяю — они уже хорошо проработаны в исходном документе.

---

## 1. Единая точка отказа на уровне инфраструктуры

**Проблема.** Весь стек — один Linux-хост, один экземпляр PostgreSQL, один RabbitMQ, один Redis. `worker` масштабируется (`replicas`), но `api` — нет (в `docker-compose.yml` для `api` не задан `deploy.replicas`, при этом WS/REST — единственная внешняя поверхность для оператора и для BC). Падение хоста, диска или процесса `postgres`/`rabbitmq` останавливает всю печать компании одновременно — на неё завязаны и печать, и генерация PDF, и обмен файлами.

**Почему это важно.** Раздел 9 подробно описывает graceful-деградацию при недоступности NST (readiness не зависит от NST), но ни слова не говорит о деградации при недоступности самой брокерской/БД-инфраструктуры — а это тот случай, который выключает систему целиком, а не частично.

**Рекомендации:**
- Явно зафиксировать в плане, что MVP сознательно работает как single-host (это нормальное решение для старта), но добавить в раздел 9 пункт про RTO/RPO и процедуру восстановления хоста целиком (создание нового хоста из `docker-compose.yml` + `ops/backup/*` + `volumes/`) — сейчас есть скрипты бэкапа, но нет описанной процедуры *restore*, тем более — проверенной вживую.
- Для `api` добавить `deploy.replicas` за reverse proxy с балансировкой (даже 2 реплики снимают риск падения процесса), особенно если WS уже спроектирован через Redis Pub/Sub — он и так готов к multi-instance fanout.
- Отдельно продумать план перехода на RabbitMQ-кластер (mirrored/quorum queues) и Postgres-репликацию как эволюцию после MVP, а не как то, что можно забыть навсегда — иначе легко закостенеет как "временное" решение.

## 2. Надёжность Redis-локов при сбоях самого Redis

**Проблема.** Раздел 9 хорошо решает проблему TTL/heartbeat для локов, но не рассматривает поведение при падении/рестарте *самого* Redis-инстанса. `--appendonly yes` спасает данные, но не гарантирует, что при рестарте Redis все активные локи корректно восстановятся или что во время недоступности Redis два воркера не решат, что лок никем не удерживается, и не возьмутся за один и тот же ресурс (файл, принтер) одновременно.

**Рекомендации:**
- Явно описать поведение хендлеров при `LOCK_TIMEOUT`/недоступности Redis: если Redis недоступен — воркер обязан отказаться от операции (fail-safe), а не выполнить её без лока "потому что лока сейчас нет".
- Для одиночного Redis без Sentinel/Cluster это приемлемо для MVP, но стоит явно пометить это архитектурным допущением (single point of coordination), а не пропускать молчанием — как минимум одной строкой в разделе 8 или 9.

## 3. Безопасность callback-эндпоинта NST: нет защиты от replay [внесено в план]

**Проблема.** Раздел 5.2/8 описывает подпись `X-Signature: HMAC-SHA256(body, NST_CALLBACK_SECRET)`, но HMAC сам по себе не защищает от повторной отправки перехваченного (или скомпрометированного) валидного запроса — атакующий, получивший один раз валидный подписанный callback, может реиграть его позже (например, повторно "напечатать статус success" для другой задачи, если `job_id`/`nst_job_ref` предсказуемы, либо просто вызвать путаницу статусов повторной отправкой того же тела).

**Рекомендации:**
- Добавить в подписываемое тело временную метку (`timestamp`) и проверять окно допустимости (например, ±5 минут), либо nonce с дедупликацией по `nst_job_ref`+`status`.
- Использовать `hmac.compare_digest` (constant-time comparison) при валидации подписи — стоит явно зафиксировать в плане как требование к реализации `security.py`, иначе это типичная ошибка на этапе кода.

## 4. Приоритет задачи — полностью доверяется клиенту

**Проблема.** `priority: 0–10` в `POST /tasks/print` (и, видимо, в других `/tasks/*`) принимается как есть от вызывающей стороны (BC, 3rd party). Ничего не мешает системе-источнику (по ошибке или намеренно) слать всё с `priority: 10`, что обнуляет смысл приоритизации и создаёт риск queue starvation для низкоприоритетных задач.

**Рекомендации:**
- Ограничить максимальный приоритет по роли/источнику вызова (например, `service`-ключ 3rd party не может ставить выше 5, только BC/operator — до 10), либо ограничить количество одновременных high-priority задач от одного источника.
- Зафиксировать это правило в разделе 8 (RBAC) как часть авторизационной модели, а не оставлять на усмотрение реализации.

---

## 5. Идемпотентность задана непоследовательно между типами задач [внесено в план]

**Проблема.** `idempotency_key` описан только для `POST /tasks/print`. Для `/tasks/generate`, `/tasks/convert`, `/tasks/workflow` — не упомянут вообще. При этом раздел 4.1 явно формулирует общее правило про идемпотентность на уровне *воркера* (по `task_id`), но не описывает защиту от дублирования на уровне *API* (повторный HTTP-запрos от BC при ретрае клиента создаст новую задачу с новым `task_id`, а значит на уровне воркера дедупликация не сработает — она защищает только от повторной доставки одного и того же сообщения, а не от повторного создания задачи).

**Рекомендации:**
- Добавить `idempotency_key` как единообразное необязательное поле для всех `POST /tasks/*`-эндпоинтов с одинаковой семантикой (уникальный индекс в БД, возврат существующего `task_id` при совпадении) — сейчас это сделано только для печати, а не напечатанный дважды PDF или дважды отправленный по FTP файл — такая же проблема, как с печатью.

## 6. Нет наблюдаемости на уровне трассировки между сервисами

**Проблема.** План предусматривает логи (`app/logs/*`, `logrotate`) и опциональный Grafana, но не описывает **сквозную трассировку** одного `task_id` через `api → outbox → RabbitMQ → worker → NST/FTP → callback`. При N воркерах и retry/backoff отладка конкретной "потерявшейся" задачи по одним логам на файловой системе — трудоёмкая ручная работа (grep по нескольким контейнерам и файлам).

**Рекомендации:**
- Логи — в структурированном формате (JSON) с обязательным `task_id`/`workflow_task_id`/`nst_job_ref` в каждой строке уже на этапе MVP — это дёшево сделать сразу и дорого добавить потом.
- Централизованный сбор логов (Loki/ELK) — не блокер для M1–M9, но стоит внести в чеклист (раздел 10) как отдельный пункт, иначе он рискует быть забытым насовсем, а не просто отложенным.
- Метрики очередей (глубина `q.*`, возраст самого старого сообщения, размер `q.dead_letter`) — раздел 10 упоминает "алерт на непустую `q.dead_letter`", но не описывает откуда берутся метрики (RabbitMQ management API / Prometheus exporter) — стоит явно выбрать источник.

## 7. Модель доверия к файлам — недооценённый риск при генерации PDF

**Проблема.** Раздел 8.1 подробно и корректно закрывает риск *загружаемых* файлов (доверие только к BC). Но `data` в `POST /tasks/generate` (шаблонизация Typst) — тоже внешний ввод, который приходит от BC и подставляется в шаблон. Инъекция через данные шаблона (Typst markup injection, если `customer`/`items[].sku` и т.п. не экранируются при рендере) не рассмотрена вовсе — считается, что раз источник входа доверенный (BC), то и содержимое полей безопасно, но это то же рассуждение, которое обычно ломается на практике (BC может подтягивать значения полей из мест, которые заполняют конечные пользователи — например, произвольный текст в описании позиции заказа).

**Рекомендации:**
- Явно указать в разделе 5.1 (`/tasks/generate`) или 8.1, что данные для шаблона проходят через экранирование средствами Typst (либо через собственный слой экранирования до рендера), даже если источник — BC, потому что "доверенный источник" не означает "доверенное содержимое каждого текстового поля".
- Ограничить глубину/размер `data` (защита от чрезмерно больших PDF/DoS через огромные массивы `items`).

## 8. Хранилище файлов: SMB-монтирование через `/etc/fstab` без учёта недоступности share

**Проблема.** Раздел 2 монтирует `//WIN-FILESRV/*` через `cifs` в `fstab` напрямую (не через `autofs`, не с опциями `soft`/таймаутами). Если Windows-шара временно недоступна (перезагрузка файлового сервера, сетевой сбой), процессы, обращающиеся к `/opt/cloudready-tasks/smb/*` внутри воркера, могут зависнуть на I/O (типичное поведение "hard" CIFS-монтирования), а не получить быструю ошибку — это блокирует воркер-процесс целиком, а не только задачу, которая работает с архивом.

**Рекомендации:**
- Добавить в опции монтирования `soft,timeo=100,retry=1` (или аналог) — предпочесть быстрый отказ (`STORAGE_WRITE_ERROR`, уже есть в разделе 6.5) над зависанием процесса.
- Явно продумать, что "зависший" воркер-процесс из-за hard-mount не будет пойман обычным healthcheck'ом (`check-stack.sh` слушает RabbitMQ/Redis/Postgres/NST, но не проверяет доступность SMB) — стоит добавить SMB в healthcheck или хотя бы таймаут на операции с файлами в `storage_client.py`.

## 9. Общая база данных между `api` и `worker` — архитектурный компромисс, не названный явно

**Проблема.** `api` и `worker` — формально разные сервисы (разные Dockerfile, разное развёртывание, `libs/common` для общих enum/DTO), но пишут в одну и ту же схему PostgreSQL напрямую (shared-database между сервисами). Это разумный и экономичный выбор для текущего масштаба, но план нигде не называет это сознательным компромиссом — а это важно, потому что при росте числа сервисов (например, появлении отдельного `outbox-relay` или `reconciler` как отдельного процесса, что уже упомянуто как опция в разделах 4.1/9) миграции схемы придётся координировать между несколькими кодовыми базами без единого владельца схемы.

**Рекомендации:**
- Зафиксировать в плане одной фразой: "shared database — сознательный выбор для текущего масштаба, `alembic`-миграции в `services/api` — единственный источник изменений схемы, `worker`/`reconciler` только читают/пишут по уже существующим таблицам, не создают миграций самостоятельно". Это снимает будущую неопределённость "кто владеет схемой", когда сервисов станет больше.

---

## 10. Аудит действий оператора отсутствует

**Проблема.** Раздел 8 вводит роль `operator` с правами `retry`/`cancel`, но нигде не описан журнал/лог того, кто и когда вызвал `cancel`/`retry` для конкретной задачи. При инцидентах ("почему эта задача была отменена?") это единственная информация, которая помогает разобраться постфактум, и её нет ни в таблице `tasks` (только `history` со статусами, без `actor`), ни отдельной audit-таблицей в чеклисте раздела 10.

**Рекомендации:**
- В `tasks.history` (раздел 5.1, `GET /tasks/{id}`) добавить поле `actor`/`triggered_by` к каждой записи истории статуса (`system`, `worker-02`, либо `user:<id>` для операторских действий) — небольшое изменение схемы, которое сильно облегчает будущее расследование инцидентов.

## Глоссарий аббревиатур

| Аббревиатура | Расшифровка | Пояснение |
|---|---|---|
| API | Application Programming Interface | программный интерфейс, через который сервисы обмениваются данными (здесь — REST API `FastAPI Container`) |
| REST | Representational State Transfer | архитектурный стиль веб-API поверх HTTP (`GET`/`POST`/…) |
| WS | WebSocket | протокол постоянного двустороннего соединения для live-обновлений статусов задач |
| SPA | Single Page Application | веб-приложение, работающее в браузере без перезагрузки страницы (здесь — Web Task Monitor) |
| MQ | Message Queue | очередь сообщений (в контексте плана — RabbitMQ) |
| AMQP | Advanced Message Queuing Protocol | протокол обмена сообщениями, который использует RabbitMQ |
| DLQ | Dead Letter Queue | очередь для задач, отклонённых после исчерпания попыток (`q.dead_letter`) |
| DLX | Dead Letter Exchange | exchange RabbitMQ, перенаправляющий отклонённые сообщения в DLQ |
| TTL | Time To Live | время жизни сообщения/токена/лока, после которого оно считается недействительным |
| JSONB | JSON Binary | бинарный формат хранения JSON в PostgreSQL с индексацией и быстрым доступом к полям |
| SQL | Structured Query Language | язык запросов к реляционным БД (используется в PostgreSQL) |
| ORM | Object-Relational Mapping | сопоставление объектов кода строкам БД (здесь — SQLAlchemy) |
| RBAC | Role-Based Access Control | управление доступом на основе ролей (`operator`, `service`) |
| JWT | JSON Web Token | формат токена аутентификации, используемый для подтверждения личности вызывающей стороны |
| OAuth2 | Open Authorization 2.0 | протокол авторизации, по которому Business Central выдаёт токены (client credentials flow) |
| JWKS | JSON Web Key Set | набор публичных ключей для проверки подписи JWT-токенов |
| HMAC | Hash-based Message Authentication Code | код проверки подлинности сообщения на основе хэш-функции и общего секрета (подпись callback от NST) |
| SHA-256 | Secure Hash Algorithm 256-bit | конкретная хэш-функция, используемая в HMAC-SHA256 |
| TLS | Transport Layer Security | протокол шифрования соединения (используется в HTTPS, FTPS, защищённом SFTP-подключении) |
| FTP / FTPS / SFTP | File Transfer Protocol / FTP Secure / SSH File Transfer Protocol | протоколы передачи файлов; FTPS — FTP поверх TLS, SFTP — передача файлов поверх протокола SSH |
| SSH | Secure Shell | защищённый протокол удалённого доступа, на котором базируется SFTP |
| SMB / CIFS | Server Message Block / Common Internet File System | протокол доступа к сетевым папкам Windows (используется для монтирования `//WIN-FILESRV/...`) |
| NST | Navision Service Tier | сервисный уровень Microsoft Dynamics NAV/Business Central, здесь выступает шлюзом печати |
| BC | Business Central | ERP-система Microsoft Dynamics 365 Business Central — источник документов и заданий на печать |
| DTO | Data Transfer Object | объект для передачи структурированных данных между слоями/сервисами |
| DNS | Domain Name System | система разрешения доменных имён в сетевые адреса |
| LAN | Local Area Network | локальная сеть предприятия |
| IP | Internet Protocol | сетевой протокол адресации (в контексте — LAN-адрес хоста) |
| HTTP / HTTPS | HyperText Transfer Protocol / … Secure | протокол передачи веб-данных / его защищённая (TLS) версия |
| CRUD | Create, Read, Update, Delete | базовый набор операций над сущностями (задачами, документами и т.д.) |
| MVP | Minimum Viable Product | минимальная работоспособная версия продукта, с которой начинается разработка (раздел 11 плана) |
| SPOF | Single Point of Failure | единая точка отказа — компонент, падение которого останавливает всю систему |
| RTO | Recovery Time Objective | целевое время восстановления системы после сбоя |
| RPO | Recovery Point Objective | допустимый объём потери данных при сбое, измеряемый временем с последнего бэкапа |
| MTTR | Mean Time To Recovery | среднее время восстановления после инцидента |
| DoS | Denial of Service | отказ в обслуживании — перегрузка системы, приводящая к её недоступности |
| CI/CD | Continuous Integration / Continuous Delivery (Deployment) | автоматизация сборки, тестирования и развёртывания кода |
| PID | Process ID | идентификатор процесса в операционной системе |
| UID / GID | User ID / Group ID | идентификаторы пользователя и группы в Linux, используются при монтировании SMB (`uid=1000,gid=1000`) |
| MIME | Multipurpose Internet Mail Extensions | стандарт указания типа содержимого файла (используется при проверке загружаемых файлов) |
