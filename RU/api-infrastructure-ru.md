# Организация REST API-инфраструктуры

## Задачи, которые можно делегировать собственному REST API

Под «собственным REST API» здесь понимается отдельный управляемый сервис, доступный Business Central SaaS по HTTPS. В BC должны остаться бизнес-правила, подготовка данных и сохранение результата, а сервису следует передавать только технические операции, недоступные или неудобные в AL.

| Задача | Пригодность | Что делегировать REST API |
|---|---|---|
| Объединение PDF | Высокая | Принимать несколько PDF как multipart/base64 или по временным защищённым URL, объединять их и возвращать итоговый PDF. При необходимости сервис также может заполнять шаблоны и извлекать страницы/вложения. |
| PDF Template Management | Высокая | Заменить PDFTK/Aspose: наложение шаблонов, заполнение полей, штампы, конвертацию и другие операции с PDF. Шаблоны можно хранить в BC и передавать сервису на время запроса либо версионировать в сервисе. |
| Штрихкоды | Высокая | Генерировать PNG/SVG/PDF по типу кода и значению. Для обычных штрихкодов сначала стоит проверить стандартный barcode provider/font BC — REST API нужен только для неподдерживаемых форматов или сложных этикеток. |
| PDF-этикетки и серверные принтеры | Высокая | Принимать документ и идентификатор принтера, помещать задание в очередь локального print agent и возвращать ID/статус печати. Сам REST API не сможет печатать в локальной сети без установленного там агента. |
| FTP/SFTP и SafeQueFile | Высокая | Выполнять передачу файлов, polling каталогов/очередей, повторные попытки, дедупликацию и архивирование. BC взаимодействует только с HTTPS API и получает стабильный идентификатор операции. |
| SQL management и HPL складские остатки | Высокая | Изолировать доступ к SQL/HPL: API выполняет разрешённые параметризованные запросы и возвращает типизированный JSON. Нельзя предоставлять BC универсальный endpoint для произвольного SQL. |
| FinStat | Средняя/высокая | Сделать адаптер к FinStat, централизовать API credentials, retry/cache и преобразование ответа в стабильный внутренний контракт. Если FinStat уже предоставляет совместимый REST API, BC может вызывать его напрямую без дополнительного сервиса. |
| Перевозчики | Средняя/высокая | Создать единый gateway для GLS/DPD/GEIS/TNT/FedEx: авторизация, преобразование форматов, SOAP/REST, получение этикетки, retry и журнал технических запросов. Бизнес-выбор перевозчика и данные посылки оставить в BC. |
| EDI, SKF, Škoda Auto и Eračun | Средняя/высокая | Делегировать транспорт, подпись/шифрование, AS2/SFTP, валидацию XSD и преобразование внешних форматов. Формирование и проведение бизнес-документов должно остаться в BC. |
| NCH | Средняя | Вынести файловый/сетевой обмен и при необходимости преобразование формата. Таможенные бизнес-проверки и создание записей оставить в BC. |
| Изображения на сканерах | Средняя | Делегировать resize, rotation, конвертацию, OCR и временное хранение больших файлов. Обычная загрузка и хранение Media/BLOB могут выполняться непосредственно в BC. |
| WebService Management | Низкая/средняя | Собственный API оправдан как gateway при сложной аутентификации, закрытой сети или необходимости стабилизировать контракт старого SOAP-сервиса. Обычный публичный REST/SOAP endpoint лучше вызывать напрямую через AL `HttpClient`. |
| Общие export/XML functions, Excel Buffer, Mail Record, командировки, страницы Assembly/E-ShopData, Develop Import, Export Segment, Complete BOM XML | Низкая | Эти задачи в основном состоят из логики BC и стандартных операций AL со stream/XML/Excel/BLOB. Выносить их целиком в REST API не следует; сервис нужен только для конкретного внешнего транспорта, SQL, тяжёлой конвертации или неподдерживаемого формата. |

### Общие требования к REST API

- HTTPS и аутентификация через OAuth 2.0 client credentials, managed identity или короткоживущие токены; секреты не хранить в AL-коде.
- Идемпотентность для печати, EDI и файлового обмена: BC передаёт уникальный operation ID, повторный запрос не создаёт дубль.
- Асинхронная модель (`202 Accepted` + status endpoint) для печати, больших PDF, FTP/SFTP и долгих SQL-отчётов.
- Ограничения размера, timeout, retry с backoff, correlation ID и журнал без персональных данных/секретов.
- Версионированный контракт (`/api/v1/...`), машинно-читаемые коды ошибок и health endpoint.
- Для каждого API-сценария предусмотреть AL client codeunit, setup table/page, permissions и интеграционные тесты.

## Рекомендуемый стек REST API и Docker Compose

Основной рекомендуемый вариант — Linux containers. Все зависимые компоненты REST API запускаются локально на сервере заказчика в одном Docker Compose. Windows может оставаться операционной системой host, если Docker использует Linux backend через WSL2 или Hyper-V.

### Необходимость внутреннего Linux-сервера

Для production рекомендуется выделить отдельный внутренний Linux-сервер или Linux VM. Размещать Docker Compose непосредственно на Windows-сервере Business Central через Docker Desktop/WSL2 не следует: это усложняет сопровождение, обновление и разделение ресурсов. Сервер остаётся внутри инфраструктуры заказчика и не требует публикации в интернет.

На Linux-сервере размещаются:

- Docker Engine и Docker Compose;
- FastAPI и фоновые workers в отдельных Docker-контейнерах;
- Typst и средства обработки PDF;
- RabbitMQ, PostgreSQL и при необходимости Redis/MinIO;
- reverse proxy, мониторинг и технические логи;
- постоянные volumes и процедуры их резервного копирования.

Business Central On-Prem на Windows обращается к внутреннему DNS-имени API по HTTPS, например `https://bc-api.company.local`. Между серверами достаточно открыть HTTPS-порт API; административные порты PostgreSQL, RabbitMQ, MinIO и Docker наружу не публикуются. Доступ Linux-сервера в интернет разрешается только к явно необходимым внешним API перевозчиков, FinStat, EDI и репозиториям обновлений.

Linux-сервер должен иметь статический IP/DNS, доверенный TLS-сертификат, синхронизацию времени, контролируемые обновления, мониторинг свободного места и backup volumes/БД. Его ресурсы необходимо отделить от SQL Server и Business Central Service Tier, чтобы обработка PDF или массовый обмен файлами не влияли на работу BC.

Для начальной оценки достаточно 4 CPU, 8 GB RAM и отдельного диска от 100 GB; окончательный размер определяется объёмом PDF, числом параллельных workers и сроком хранения файлов. Для production предпочтительна Linux VM с поддерживаемым LTS-дистрибутивом, например Ubuntu Server LTS или Debian stable.

### Компоненты

FastAPI и все непосредственно связанные сервисы запускаются в Docker-контейнерах и управляются общим файлом Docker Compose. Каждый сервис (`reverse-proxy`, `api`, workers, scheduler, RabbitMQ, PostgreSQL, а также опциональные Redis, MinIO и observability) работает в отдельном контейнере внутри приватной Docker network. Эти прикладные сервисы не устанавливаются непосредственно на Linux host. Наружу публикуется только HTTPS-порт контейнера `reverse-proxy`; внутренний порт FastAPI и порты остальных сервисов доступны только контейнерам. Постоянные данные хранятся в именованных Docker volumes и не зависят от жизненного цикла отдельных контейнеров.

| Сервис | Технология | Назначение |
|---|---|---|
| reverse-proxy | Nginx или Traefik | TLS, маршрутизация, лимиты запросов |
| api | Python 3.13, FastAPI, Uvicorn, Pydantic | REST/OpenAPI-контракт для BC, аутентификация и операции |
| worker-documents | Celery, Typst, pikepdf | Создание и обработка PDF |
| worker-integrations | Celery, HTTPX, lxml, Paramiko | Перевозчики, FinStat, EDI, REST/SOAP и SFTP/FTP |
| scheduler | Celery Beat | Периодические задания, polling и очистка |
| rabbitmq | RabbitMQ | Надёжная очередь заданий |
| postgres | PostgreSQL, SQLAlchemy, Alembic | Операции, статусы, настройки, идемпотентность и аудит |
| redis | Redis, опционально | Кэш токенов, rate limiting и короткие блокировки |
| minio | MinIO, опционально | Локальное S3-совместимое хранилище документов |
| observability | OpenTelemetry, Prometheus/Grafana опционально | Метрики, traces и диагностика |

### Typst и PDF

- Typst является основным движком генерации новых PDF, печатных форм и этикеток.
- Шаблон получает JSON; шаблоны, fonts и assets версионируются.
- Typst запускается в отдельном worker-контейнере с ограничениями CPU, памяти, времени и размера входа.
- pikepdf используется для объединения, разделения и перестановки страниц существующих PDF.
- Результат сохраняется в Docker volume или MinIO и возвращается BC как stream либо по короткоживущей защищённой ссылке.

### Минимальная первая версия

~~~text
reverse-proxy
api
worker-documents
rabbitmq
postgres
~~~

Документы и Typst-шаблоны можно сначала хранить в именованных volumes. MinIO, Redis, integration worker и observability добавляются по мере необходимости.

~~~yaml
volumes:
  postgres_data:
  rabbitmq_data:
  document_data:
  typst_templates:
~~~

Volumes должны быть привязаны к отдельному каталогу данных, а не к каталогам Business Central. Для production нужны backup, healthchecks, фиксированные версии images, контролируемое обновление и ротация логов.

### Сетевая схема

~~~text
Business Central On-Prem
          │ HTTPS
          ▼
     reverse-proxy
          │
          ▼
        FastAPI ───── PostgreSQL
          │
          ▼
       RabbitMQ
          │
          ├── Typst/PDF worker
          └── integration worker ── перевозчики / FinStat / EDI / SFTP
~~~

Наружу публикуется только HTTPS-порт reverse proxy. PostgreSQL, RabbitMQ, Redis и MinIO остаются во внутренней Docker network.

### Печать

Linux-контейнер не должен напрямую управлять Windows Print Spooler. Для Windows-принтеров используется Print Agent как отдельная Windows-служба на host или print server. Если принтеры доступны через IPP/CUPS, print service можно разместить в Compose.

## Сложности реализации на Windows containers

Если Linux containers, WSL2 и Linux VM запрещены, Compose должен работать в настоящем режиме Windows containers. Это возможно для собственных Python-сервисов, но заметно усложняет инфраструктуру:

- официальные образы PostgreSQL, RabbitMQ, Redis, MinIO, Nginx и Typst преимущественно рассчитаны на Linux; понадобятся замены, установка вне Compose или самостоятельно поддерживаемые Windows images;
- Windows Server Core images значительно больше и требуют совпадения версии базового image с Windows host;
- меньше готовых образов, примеров, healthchecks и средств диагностики;
- обновление ОС и базовых images сложнее, а restart контейнеров обычно дольше;
- работа с ACL, bind mounts, сертификатами и service accounts требует Windows-специфичной настройки;
- прямой доступ контейнера к host Print Spooler всё равно ненадёжен и не отменяет необходимость Print Agent;
- Typst нужно устанавливать из Windows binary в собственный image и отдельно проверять fonts и рендеринг;
- Python-пакеты с native dependencies должны иметь совместимые Windows wheels либо потребуют build toolchain.

Возможный Windows-only компромисс:

- FastAPI, Typst worker и integration worker — собственные Windows Server Core containers;
- IIS/ARR — reverse proxy на Windows host;
- SQL Server — отдельная база операций вне Compose;
- таблица operations в SQL Server — очередь вместо RabbitMQ/Celery;
- Windows volumes — вместо MinIO;
- Windows Print Agent — отдельная служба.

Этот вариант допустим для одного сервера и умеренной нагрузки, но хуже переносится и масштабируется. Поэтому Linux containers остаются рекомендуемым вариантом, даже если физический host работает под Windows.
