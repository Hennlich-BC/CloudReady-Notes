# Перенос серверной печати из Business Central на Linux API

## Исходная и целевая схема

Сейчас печать выполняется синхронно на Windows-сервере:

~~~text
Business Central on-prem
  -> сохраняет файл во временный каталог
  -> запускает SumatraPDF
  -> SumatraPDF передаёт PDF, имя принтера и параметры в Windows Print Spooler
~~~

Цель — перенести приём и диспетчеризацию заданий в API на Linux VM:

~~~text
Business Central
  -> HTTPS: документ + printerId + параметры + operationId
  -> Linux API / очередь / print worker
  -> CUPS/IPP или Windows Print Agent
  -> принтер
~~~

SumatraPDF нельзя просто перенести на Linux: это Windows-приложение, и его разработчики не планируют версию для других ОС ([официальная документация SumatraPDF](https://www.sumatrapdfreader.org/docs/Why-only-Windows)). На Linux его роль обычно выполняет CUPS: он принимает PDF, ставит задание в очередь, при необходимости преобразует документ и отправляет его принтеру. CUPS умеет принимать PDF напрямую и предоставляет команды `lp`/`lpr`, C API и IPP-интерфейс ([OpenPrinting CUPS](https://openprinting.github.io/cups/)).

## Варианты реализации

| Вариант | Когда подходит | Плюсы | Ограничения |
|---|---|---|---|
| **1. Linux API + CUPS + прямой IPP/IPPS к принтерам** | Современные сетевые принтеры поддерживают IPP Everywhere/AirPrint | Рекомендуемый вариант; Windows-сервер больше не участвует; стандартные параметры, очередь и статусы | Нужно проверить модель каждого принтера, сетевой доступ и поддерживаемые media/tray/finishing options |
| **2. Linux API + отдельный корпоративный CUPS print server** | Принтеров много, нужны централизованные очереди, ACL и единое администрирование | API не управляет драйверами; печать отделена от прикладного сервиса; проще масштабировать | Появляется ещё один инфраструктурный компонент |
| **3. Linux API + Windows Print Agent** | Нужен Windows-only драйвер, специальный лоток/финишер или точное сохранение поведения SumatraPDF | Максимальная совместимость с текущими принтерами и драйверами | Windows print server остаётся; нужно разработать и сопровождать агент |
| **4. Linux API + CUPS/Samba к общей Windows-очереди** | Временный переходный вариант, когда Windows-очередь уже опубликована | Меньше изменений в print server | Сложнее аутентификация и диагностика; Linux всё равно должен сформировать понятный принтеру поток; не лучший целевой вариант |
| **5. Прямая RAW-печать на порт 9100** | Этикеточные принтеры и уже готовые ZPL/EPL/PCL/PS-файлы | Просто и быстро, сохраняется очередь CUPS | Нельзя считать, что произвольный принтер примет PDF; почти нет нормализованных возможностей и статусов |

### Вариант 1 — рекомендуемый

На Linux VM устанавливается CUPS. Для каждого физического принтера создаётся фиксированная очередь, например:

~~~bash
lpadmin -p warehouse_a4 -E \
  -v "ipps://printer-01.company.local/ipp/print" \
  -m everywhere
~~~

Для современных устройств предпочтителен driverless-режим IPP Everywhere. Поддержка старых PPD-драйверов и raw queues в CUPS устаревает, поэтому новую архитектуру не следует строить вокруг legacy PPD, если принтер поддерживает IPP ([Printer Applications and Printer Drivers](https://openprinting.github.io/cups/drivers.html)). IPP Everywhere требует стандартные растровые форматы, а PDF является рекомендуемым форматом, но не обязательным для каждого устройства; фактические форматы нужно проверить через атрибут `document-format-supported` ([PWG IPP Everywhere](https://www.pwg.org/ipp/everywhere.html)). CUPS может выполнить необходимое преобразование, если установлен подходящий filter/Printer Application.

Worker передаёт PDF в CUPS, например:

~~~bash
lp -d warehouse_a4 \
  -n 2 \
  -o media=A4 \
  -o sides=two-sided-long-edge \
  -o print-quality=4 \
  -t "BC operation 7d83..." \
  -- /spool/7d83/document.pdf
~~~

CUPS поддерживает выбор принтера, число копий, формат бумаги, duplex, ориентацию, диапазон страниц и другие стандартные параметры; специфические возможности очереди можно получить командой `lpoptions -p <queue> -l` ([документация `lp`](https://openprinting.github.io/cups/doc/man-lp.html), [параметры командной печати](https://openprinting.github.io/cups/doc/options.html)).

CUPS разумно запускать отдельным сервисом от FastAPI/worker. Для сетевых принтеров возможны два размещения:

- CUPS на Linux host, а print worker обращается к нему по IPP через закрытый локальный интерфейс;
- отдельный CUPS-контейнер с постоянным volume для конфигурации и явным доступом к сети принтеров.

Host-вариант обычно проще в эксплуатации. Для USB-принтеров контейнеризация дополнительно требует проброса устройств и правил доступа.

### Вариант 2 — отдельный CUPS print server

API сохраняет только логическое соответствие `printerId -> CUPS queue` и отправляет задание на выделенный сервер печати. Этот вариант предпочтительнее, если принтеров десятки, ими пользуются несколько систем или сопровождение принтеров выполняет отдельная команда. API и CUPS можно обновлять независимо.

### Вариант 3 — Windows Print Agent

Если тест CUPS не воспроизводит текущий результат, Windows-служба остаётся рядом с Windows Print Spooler. Linux API сохраняет задание в PostgreSQL/object storage, а агент исходящим HTTPS-запросом забирает задания, скачивает PDF, печатает через SumatraPDF или Windows API и сообщает статус обратно.

Рекомендуется pull-модель: Linux не открывает административные порты Windows и не получает удалённый доступ к spooler. Агент аутентифицируется собственным сертификатом или короткоживущим токеном. Несколько агентов могут обслуживать разные площадки.

Этот вариант нужен, если используются:

- принтеры только с Windows-драйвером;
- нестандартные названия лотков, степлер, финишер или vendor-specific settings;
- печать через уже существующие Windows-очереди с доменными правилами;
- PDF, которые выглядят иначе после Linux-рендеринга.

### Варианты 4 и 5 — специальные или переходные

Доступ из CUPS к Windows shared printer через Samba технически возможен, но добавляет учётные данные и плохо изолирует ответственность за преобразование документа. Если Windows print server предоставляет IPP, лучше сначала проверить IPP-подключение.

RAW/AppSocket (`socket://printer:9100`) следует использовать для printer-ready данных. Например, ZPL можно отправлять как есть на Zebra-совместимый принтер. PDF через RAW допустим только после подтверждения, что конкретная модель поддерживает PDF natively. CUPS документирует IPP/IPPS, LPD и AppSocket как штатные backends ([администрирование CUPS](https://openprinting.github.io/cups/doc/admin.html)).

## Рекомендуемая архитектура API

~~~text
BC --HTTPS--> FastAPI --PostgreSQL--> job status
                    |
                    +--> object storage / spool volume
                    |
                    +--> RabbitMQ --> print worker --> CUPS --IPP/IPPS--> printer
                                               \
                                                `--HTTPS--> Windows agent (fallback)
~~~

Печать должна быть асинхронной. HTTP timeout не означает, что принтер закончил печатать, а автоматический повтор запроса BC без идемпотентности может напечатать документ дважды.

Минимальный контракт:

~~~http
POST /api/v1/print-jobs
Idempotency-Key: <operationId from BC>
Content-Type: multipart/form-data

file=<PDF>
metadata={
  "printerId": "warehouse-a4",
  "copies": 2,
  "media": "A4",
  "sides": "two-sided-long-edge",
  "orientation": "portrait"
}

202 Accepted
{
  "jobId": "...",
  "status": "accepted"
}
~~~

Дополнительные endpoints:

- `GET /api/v1/print-jobs/{jobId}` — текущий статус и безопасное описание ошибки;
- `POST /api/v1/print-jobs/{jobId}/cancel` — отмена, если задание ещё можно остановить;
- `GET /api/v1/printers` — только разрешённые логические принтеры и допустимые параметры;
- `GET /health/live` и `GET /health/ready` — состояние API, очереди и CUPS.

Статусы API: `accepted -> queued -> submitted -> processing -> completed`, а также `failed` и `canceled`. CUPS/IPP предоставляет операции Print-Job, Get-Job-Attributes и Cancel-Job ([реализация IPP в CUPS](https://openprinting.github.io/cups/doc/spec-ipp.html)). При этом `completed` означает, что очередь/устройство сообщило о завершении задания; это не является гарантией, что бумага физически вышла и была получена пользователем.

Для MVP worker может вызывать `lp` как subprocess и извлекать CUPS job ID из результата. Для долгосрочной реализации можно использовать libcups/IPP client и получать структурированные атрибуты без разбора текста CLI. В обоих случаях аргументы передаются массивом, без shell.

## Соответствие текущего и нового процесса

| Текущий шаг | Новый шаг |
|---|---|
| BC сохраняет временный файл | API потоково принимает PDF и сохраняет его под server-generated ID |
| BC выбирает Windows printer name | BC передаёт стабильный логический `printerId`; реальный URI хранится только в конфигурации сервиса |
| BC формирует строку параметров SumatraPDF | BC передаёт типизированный JSON; API проверяет значения по allowlist конкретного принтера |
| BC запускает EXE | API создаёт асинхронное задание, worker отправляет его в CUPS/агент |
| Код возврата процесса считается результатом | BC опрашивает status endpoint по `jobId` |
| Временный файл удаляется после процесса | Файл удаляется после terminal status и настраиваемого retention period |

## Ручная настройка принтеров в CUPS

После подключения принтера его параметры можно настроить через встроенный веб-интерфейс CUPS:

~~~text
http://linux-server:631
  -> Printers
  -> выбрать принтер
  -> Administration
  -> Set Default Options
~~~

В зависимости от возможностей устройства доступны:

- формат и тип бумаги;
- лоток подачи;
- односторонняя или двусторонняя печать;
- цветной или монохромный режим;
- качество и разрешение;
- ориентация и масштабирование;
- сортировка копий;
- финишер, степлер и vendor-specific функции.

Интерфейс CUPS также позволяет добавить или удалить принтер, напечатать тестовую страницу, приостановить очередь, отменить задание и посмотреть состояние принтера. Для удалённого использования Web UI необходимо отдельно разрешить сетевой доступ в конфигурации CUPS. Административный интерфейс не следует публиковать в интернет: его нужно ограничить административной VLAN, VPN или списком доверенных адресов и защитить аутентификацией и TLS.

### Три уровня настроек

Следует различать настройки очереди, отдельного задания и самого устройства.

| Уровень | Примеры | Где применяется и хранится |
|---|---|---|
| Очередь CUPS | A4 по умолчанию, duplex, чёрно-белая печать, основной лоток | Server-side defaults CUPS; применяются, если задание не передало другое значение |
| Отдельное задание | 3 копии, A5, цвет, диапазон страниц | Передаются API в CUPS вместе с заданием и сохраняются в записи print job для аудита |
| Аппаратная конфигурация | IP-адрес, firmware, установленные лотки, тип бумаги в лотке, калибровка | В самом принтере; обычно изменяется через его встроенный Web UI |

Server-side defaults можно задать через CLI:

~~~bash
lpadmin -p office-printer \
  -o media=A4 \
  -o sides=two-sided-long-edge \
  -o print-color-mode=monochrome
~~~

Параметры, поддерживаемые конкретной очередью, можно вывести командой:

~~~bash
lpoptions -p office-printer -l
~~~

Параметры одного задания передаются через `lp` и не изменяют defaults очереди:

~~~bash
lp -d office-printer \
  -n 3 \
  -o media=A5 \
  -o sides=one-sided \
  -o print-color-mode=color \
  -- document.pdf
~~~

Для driverless-принтера CUPS получает его возможности динамически через IPP `Get-Printer-Attributes`: размеры бумаги, duplex, цветовые режимы, разрешения, лотки и поддерживаемые форматы документов. Поэтому наличие отдельного PPD-файла не требуется. Фактический список параметров зависит от модели и firmware принтера.

### Где CUPS сохраняет данные

Основная конфигурация находится в `/etc/cups`. Конкретное расположение отдельных runtime-файлов может немного отличаться в зависимости от Linux-дистрибутива.

| Путь | Назначение |
|---|---|
| `/etc/cups/printers.conf` | Очереди, URI устройств, состояние и server-side настройки принтеров |
| `/etc/cups/cupsd.conf` | Сетевой доступ, аутентификация, права и общая конфигурация CUPS |
| `/etc/cups/cups-files.conf` | Пользователи, группы и расположение служебных файлов |
| `/etc/cups/lpoptions` | Системные defaults/instances, созданные через `lpoptions` |
| `~/.cups/lpoptions` | Defaults конкретного Linux-пользователя |
| `/etc/cups/ppd/` | PPD-файлы legacy-принтеров; для IPP Everywhere обычно не нужны |
| `/var/spool/cups/` | Активные задания и spool-данные |
| `/var/log/cups/` | Журналы CUPS, если дистрибутив не перенаправляет их в system journal |

Конфигурационные файлы CUPS не следует редактировать напрямую. Для изменений нужно использовать Web UI, `lpadmin`, `lpoptions` или IPP: CUPS управляет файлами самостоятельно и может перезаписать ручные изменения. Доступ к файлам необходимо ограничить, поскольку конфигурация очереди может содержать чувствительные сведения о подключении.

При контейнерном размещении как минимум `/etc/cups` и необходимые spool/state-каталоги должны находиться в persistent volumes. Без этого очереди и настройки исчезнут при пересоздании контейнера. Для CUPS на Linux host эта конфигурация сохраняется обычными средствами ОС и должна входить в backup.

### Профили печати для Business Central

Для одного физического принтера можно создать несколько логических профилей, например:

~~~text
office-a4-color   -> A4, цвет, односторонняя
office-a4-duplex  -> A4, ч/б, двусторонняя
office-invoices   -> A4, ч/б, Tray 2
~~~

Профили могут быть отдельными CUPS instances/очередями, но бизнес-доступ лучше контролировать в API. Рекомендуемое разделение ответственности:

- **CUPS** хранит URI принтера, технические возможности и defaults очереди;
- **физический принтер** хранит сетевые и аппаратные настройки;
- **API** хранит соответствие `printerId -> CUPS queue`, разрешённые параметры, бизнес-профили и ограничения;
- **PostgreSQL** хранит фактические параметры и статусы каждого print job;
- **Business Central** передаёт логический `printerId`, выбранный профиль и только разрешённые overrides.

Пример конфигурации API:

~~~yaml
printers:
  office-invoices:
    cups_queue: office-printer
    allowed_options:
      media: [A4]
      sides: [one-sided, two-sided-long-edge]
      copies_max: 5
    defaults:
      media: A4
      sides: one-sided
      print-color-mode: monochrome
~~~

Так BC не зависит от внутренних имён очередей и не может передать произвольную CUPS-опцию. Изменение IP-адреса или замена принтера выполняются на стороне CUPS/API без модификации AL-кода.

## Безопасность и надёжность

- Нельзя принимать от BC произвольный URI/hostname принтера или произвольные аргументы `lp`; только `printerId` и проверенный набор параметров.
- Проверять MIME/signature PDF, размер, число страниц и при необходимости шифрование/пароль PDF.
- Один `Idempotency-Key` должен возвращать уже созданное задание, а не печатать копию повторно.
- Хранить файлы под случайными ID вне web root; исходное имя использовать только как display metadata.
- Ограничить service account: право печати, но не администрирование CUPS. Не публиковать CUPS UI наружу.
- Использовать IPPS/TLS там, где это поддерживает принтер или print server. CUPS поддерживает TLS и настраиваемую проверку сертификатов ([CUPS encryption](https://www.cups.org/doc/encryption.html)).
- Задать максимальное число одновременных заданий на очередь, retry только для явно временных ошибок и dead-letter queue для ручного разбора.
- Не повторять автоматически задание с неопределённым результатом после потери связи: сначала сверить CUPS job ID, иначе возможен дубль.
- Логировать correlation ID, BC operation ID, printerId, CUPS job ID, переходы статусов и код ошибки, но не содержимое PDF.
- Настроить retention и гарантированную очистку spool-файлов, включая задания, завершившиеся аварийно.

## Как выбрать вариант

Перед разработкой нужен короткий технический pilot на реальных устройствах:

1. Собрать модели принтеров, firmware, текущие Windows-драйверы и используемые параметры SumatraPDF.
2. Проверить сетевой маршрут Linux VM до принтеров и наличие IPP/IPPS; не полагаться только на наличие порта 9100.
3. Создать CUPS queue `-m everywhere`, получить поддерживаемые параметры и напечатать эталонные PDF.
4. Сравнить масштаб, поля, шрифты, штрихкоды, duplex, лотки, копии и этикетки с текущей печатью.
5. Принтеры, прошедшие тест, направить напрямую через CUPS; несовместимые — через Windows Print Agent.

Итоговая рекомендация: начать с **варианта 1 (FastAPI worker + CUPS + IPPS/IPP Everywhere)** и оставить **вариант 3 (Windows Print Agent)** как совместимый fallback. Такая гибридная схема позволяет убрать Windows из большинства заданий, не блокируя миграцию из-за одного legacy-принтера или vendor-specific функции.
